How it works, and how it should work in production

A hotel payment goes guest to processor to PMS folio. Synthetic data; the processor and the PMS are simulators.

The flow (what the demo shows)

  1. PMS to bridge: a booking event; the bridge applies the payment rule and creates a payment link.
  2. Guest to bridge: the card is tokenised the moment it arrives. Only a token comes back.
  3. Bridge to processor: authorise, then capture, with an idempotency key so a repeat never charges twice.
  4. Bridge to database: only ciphertext and a wrapped key are stored. The number is never stored, logged or returned.
  5. Bridge to PMS: the payment is posted to the reservation's folio window. If the PMS is down it waits in a dead-letter queue with the reason, and replays once.

The rules that keep money safe

  • Idempotent: the same key is the same payment, however it is repeated or raced.
  • Never lost: a captured payment is posted, or dead-lettered with a reason.
  • Unknown is not failed: after a timeout the bridge looks for its own post before posting again.
  • The PMS decides the date: the business date moves at night audit, not at midnight.
  • Reconciled: every capture is matched against the processor's settlement file and the folio.
  • Fails closed: no key mode or no gateway configured means it does not start.
