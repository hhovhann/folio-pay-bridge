# What the agents got wrong (this build)

Entries 6 to 14 come from the first review and the refactor; 15 to 22 from the security and idempotency review that followed, 23 to 27 from the simulator, coverage and demo work, 28 to 31 from the final code review, 44 to 48 from the production-readiness review, 49 from turning those lessons into enforced standards, 50 from the dependency review, 51 to 53 from moving OPERA onto Oracle's published contract, 54 and 55 from the review of that work, 56 from giving every test a readable name, 57 from re-recording the demo video, 58 to 60 from the final cleanup and review, and 61 from showing every party in a card payment. 1 to 5 are from the first build.

A pilot, not production. These are the corrections made while building it with Claude Code agents; each was caught by reading output or by a test, not by the agent noticing.

1. **Test isolation assumed a clean database.** The money-conservation test summed every row in the charge and posting tables, but earlier tests had left rows behind, so the totals were wrong (`expected 46030, was 241930`). The test failed, which is the point of it; the fix was to clean the tables between tests, not to loosen the assertion.
2. **A flaky heuristic in the PCI test.** To prove the database holds no card number, the first version ran the "looks like a card number" regex over a hex dump of random ciphertext. A random run of digits can pass the Luhn check by chance, so the test failed on some runs and not others. The fix separated the two checks: the regex on text columns, and "the real number is not in the raw bytes" on binary columns. Verified by running the full suite three times.
3. **A test helper that did not compile.** `assertThat` on a lambda result was ambiguous between overloads. Trivial, but it shows the habit: the build is the first reviewer.
4. **A demo log panel hid the evidence.** The console showed only the last nine log lines, so the line proving the card was masked had scrolled away while the narration claimed it was on screen. The demo script's assertion against the screen failed, which is why those assertions exist; the panel now shows forty lines.
5. **A payment request stayed open after the card was charged.** The first version closed a request only when charge and folio posting both succeeded. In the recorded demo the late booking showed POSTED in the ledger while its request still offered a Pay button. Found by looking at the poster frame of the finished video, not by a test; fixed to close on capture, with a test (`aLinkClosesOnCaptureEvenWhenTheFolioPostingIsWaiting`).

6. **Replay retried a rejected posting, and the test could not notice.** `replay` re-called OPERA for anything not POSTED, including `REJECTED_BY_OPERA`, while the README and D-5 said a rejection is not retried. The old test passed only because the fake rejects `F-CLOSED` every time. An independent review (a second model reading the code) caught it. Fixed with an early return, and `PostingServiceImplTest.replayingARejectedPostingNeverCallsOperaAgain` plus a mutation check: with the guard removed, two tests fail.
7. **The retry slept while the card number was in memory.** The first retry wrapped the whole `vault.withCard` call, so the decrypted number stayed live through every backoff. Found by the owner questioning the retry design, confirmed by the review. The retry now wraps each call and the vault is opened per attempt; `ChargeServiceImplTest.theCardNumberIsNotHeldWhileARetryWaitsOrDuringCapture` fails if the nesting is put back (checked by doing it).
8. **A "parallel duplicates" test that proved the fake.** The fake processor deduplicates by key, so the test passed even though a losing twin could overwrite the winner's CAPTURED with PENDING (no version column). Added `@Version` and a save-or-reload step; the integration test now asserts the stored state is CAPTURED and says in a comment what it does and does not prove.
9. **A Dockerfile that was never built.** It failed on the real Amazon Linux 2023 images (no `tar` for the Maven wrapper, no `useradd` in the headless image) while the docs presented it as the runtime. Found by the review building the images. Fixed, then verified: image build, `docker compose up`, `/actuator/health`, one payment read back from PostgreSQL.
10. **The catch-all error handler turned unknown routes into 500s.** Found by `DemoControlsOffIntegrationTest` during the refactor (a missing demo endpoint should be 404). The handler now extends Spring's `ResponseEntityExceptionHandler`.
11. **A log-masking test that asserted on empty output.** The first version of `ProductionLogConfigTest` built a standalone Logback context, which has no MDC adapter, so nothing was written and the assertion failed for the wrong reason. Read the Logback status output, fixed the harness, then removed the converter from the real config to confirm the test fails.
12. **A mutation check that restored the wrong backup.** While proving tests can fail, one restore pointed at a different temp path and left a deliberate bug in the source; the full suite failed on the next run, which is how it was noticed and put back.
13. **`check_specs.py` did not check anything about tests.** It only counted ticked boxes. It now cross-checks every ticked `Class.method` against the surefire reports, and on its first run caught a mistyped method name in the new checklists.
14. **Structure.** The first build put entity, repository and service together per feature, with concrete services, a static retry helper and a 164-line controller that reached into repositories and fakes. Called out by the owner reading the code; replaced by the layers in D-14.

15. **A fix for one bug created a worse one.** To let a guest retry a declined payment link with another card, the key became `link:<id>:<token>` per card. Nothing stopped a second card paying a link that was already PAID, so a guest could be charged twice. The independent security review reproduced it (two captures for one request). Replaced by an atomic claim (D-19) and tests that race two cards.
16. **A comment that said the opposite of the code.** `ChargeView` said the card token was "deliberately left out", but the link key carried the token and `/api/charges` returned it. Found by the review; the key now holds a hash, and `ReviewFindingsIntegrationTest.linkChargeKeysNeverContainTheCardToken` checks it.
17. **"Fail closed" that depended on one line of configuration.** The key service had `matchIfMissing = true` and the fakes were ordinary beans, so a deployment that replaced the config file would start with a throwaway key and a pretend processor. `FailClosedStartupTest` now starts the application without each setting and expects it to refuse.
18. **A mask that claimed more than it did.** `PanMasker` was documented as masking any Luhn-valid number, but digits glued to either side, dots, slashes, Unicode digits and exception text got through. Rewritten to test every window inside a digit run, with the cases from the review as tests.
19. **An incomplete fix.** The earlier version-column fix (entry 8) let a request that lost the race return the stored state even when that state was an older "pending" and the loser held the capture. Now the further-along state wins and is saved.
20. **A key that ignored where the money goes.** Repeating a payment key with a different folio or business date returned OK for the original folio. The charge now binds every field that decides the destination.
21. **A build that reported success while the tests did not compile.** After the signature changes, an incremental `./mvnw test-compile` printed BUILD SUCCESS with stale classes; only `clean` showed the real errors. From then on every verification ran `clean`.
22. **A test that set its configuration at the wrong precedence.** `FailClosedStartupTest` passed properties through the builder, where `application.properties` overrides them, so the first run failed for the wrong reason. Command-line arguments are used now.

23. **Two things the build caught while adding the HTTP simulators.** The jar now holds two main classes, and Maven refused to repackage until one was named. And the reconciliation test in the full-flow suite failed because the bridge database kept charges from earlier tests while the simulator was reset each time (six "missing in settlement"): a test-hygiene bug, confirmed from the failure output before the fix, not a code bug.

24. **Weak tests that could not see the bug they named.** "A rate limit is waited out" and "a lock conflict is retried" passed even if the simulator never sent the 429 or 409, because they only checked that the payment finally succeeded. Found while writing the simulator's own endpoint tests (one of which failed). Fixed by asserting the simulator really consumed each fault, for all four fault scenarios.
25. **Two placeholder assertions written to fill a gap.** Twice I left a trivial assertion in a test file (one asserted nothing about a card number, one asserted `null` is null). Both were caught by re-reading the file before running it and replaced by real tests (`CardRequestTest`, `PspSimControllerTest`). The habit to keep: re-read what was just written.
26. **A test client that sent a request twice.** `RestClient.create()` picked the JDK HTTP client, which tried an HTTP/2 upgrade on a cleartext POST; a throttle test got 201 instead of 429 while `curl` against the same simulator got 429. Confirmed by reproducing with curl first, then pinned the test client to HTTP/1.1 like the production adapters.
27. **A business-date lookup that made a payment fail while the PMS was down.** The dry run of the full-flow demo found that paying during an OPERA outage returned an error before the card was charged, because the bridge read the business date first. Now the last known date is used for up to 24 hours, with unit and full-flow tests, and a downstream outage is a 503, not a 500.

28. **A payment-link claim given back after the money may have moved.** The link service released its claim on any domain error, including a 409 raised when a pending charge already existed, and the idempotency check bound the business date, so after night audit the same card's retry was refused and a second card could then be charged. A unit test encoded the wrong assumption ("refused before any money moved"). Caught by the final code review (Claude Opus). Fixed by settling the claim from the stored charge, and by letting a repeat that names no date resume on the charge's own date; proven with a new fake that captures and loses every reply, then a night audit: one capture.
29. **"Posted once" checked against a PMS fake that deduplicated.** Four tests asserted one post, but the fake OPERA kept posts in a map keyed by reference, so the count could never exceed one: the same mistake as entry 8. Two parallel replays could both look, find nothing and both post. Caught by the final code review. The fake now counts every post, a lease lets one request talk to OPERA, and without the lease the HTTP simulator test sees eight folio entries.
30. **A log test that could not fail, and a mutation check that was wrong.** The "card number never logged" test read the console buffer, which is masked before it is stored. Caught by the final code review; the test now reads the raw log events. My first mutation check of the new test logged the number at DEBUG, which is switched off, and reported "missed": the mutation was wrong, not the test. At INFO it is caught.
31. **A mutation script that ran no test.** It reported the posting lease as "missed" because I joined two test classes with `+` in `-Dtest`, which is Surefire's syntax for methods of one class, so nothing ran. Caught by running the same mutation by hand, which failed both tests.

32. **Two code reviews (Claude Opus, 2026-11-18) found what the earlier fixes left.** A refused capture escaped as an unchecked error, so the hold was never released; the posting lease was a fixed two minutes whatever the timeouts were set to; a reference settled in two currencies was summed into one figure; a slow PMS reply from before night audit could undo the new business date; the runbook's container could not start (read-only root filesystem, no `wget`, health checks refused by the host allowlist). Each confirmed against the code or the built image, fixed with a test, and the fix mutation-checked.
33. **A fix that broke a test in another class.** The new "do not ask a failed PMS again for 30 s" rule carried over between tests that share one Spring context, so a later test saw yesterday's date. Caught by `FullFlowHttpIntegrationTest`; the quiet period became configurable and is zero there.
34. **Two tests that kept passing after they stopped testing anything.** After the lease change the posting service worked on the object the test double returned, so "a request that loses the race carries its post onto the stored row" no longer exercised the merge at all. Caught by the coverage report (the merge lines went uncovered while the tests stayed green); the double now returns a fresh copy for the attempt and the stored row on reload.
35. **Two mutations survived.** Treating an unknown API key as anonymous still ended in 401 on the API, and re-reading already-announced rows was masked by the unique constraint. Both tests were strengthened to the behaviour that matters (a wrong key beside a valid token; a backlog larger than one batch) and the mutations were then caught.
36. **An assertion about a reply the client never sees.** I asserted the processor's `BAD_API_KEY` code reached the error message on a 401; the JDK HTTP client does not hand over that body. The run failed; the assertion was removed rather than the code bent to it.
37. **A first draft with a nonsense query.** My first reconciliation rewrite called `findByStatus` twice behind a meaningless condition. Caught by re-reading the file before compiling.
38. **A choice the owner overruled for the better.** For authentication I first built a hand-written API-key filter to avoid a new dependency. The owner asked for what payment platforms do; it was replaced by Spring Security (OAuth2 resource server plus hashed, scoped API keys). The session's own safety check blocked adding the dependencies until the owner confirmed them explicitly, as `CLAUDE.md` rule 7 requires.
39. **An optimisation that broke the folio, caught by the demo's dry run.** To spare payments the PMS timeout during an outage, I stopped asking a failed PMS for 30 s. Every unit and integration test passed. The full-flow dry run, which drives the Docker stack and asserts each line of narration, then failed: OPERA came back after a night audit, the bridge kept yesterday's date, and the posting was rejected for good. Removed, with a test that pins the opposite, and D-33 records why.
40. **The final code review (Claude Opus, high effort) found ten more, all confirmed.** The new remote-creation API shared its namespace with booking references, so an app could replace a booking's deposit link; a processor 401 (our rotated key) declined the guest's card for good; reconciliation sent every id in one `IN` list, past PostgreSQL's parameter limit; two identical link requests could still race into a 409; multipart bodies skipped the size limit; the webhook relay rescanned all history every five seconds; logging whole exceptions relied on the Luhn mask (against hard rule 1); the health exemption matched a raw path prefix; and two smaller ones. Each fixed with a test, and each fix mutation-checked.
41. **A rule stated too strongly.** To stop a slow PMS reply from undoing night audit I made the remembered business date "never go back". An integration test from an earlier phase, which moves the PMS date back on purpose, failed once a new test changed the run order: the bridge ignored the PMS's own newer answer. The rule is now about order, not dates: an answer is stale only if the answer to a later request already arrived. Both behaviours have a test.
42. **A published video with the wrong voice, uploaded without checking the file.** The narrated video was recorded with the Kokoro voice, then overwritten on disk by a recording made with a silent macOS fallback voice, and I uploaded that file to the release without re-checking it. Caught by the owner, who heard the difference. Confirmed from the audio (22.05 kHz instead of Kokoro's 24 kHz). The recorder now refuses to run without the Kokoro models unless a stand-in voice is asked for by name, prints the voice it used, and the file's sample rate and length are checked before any upload.
43. **A guardrail with a gap.** The project's permission rules denied `git push --force` to agents but not `git push --force-with-lease`, which is also a force-push; the owner had approved that push, and it went through. Found while doing the next force-push, which the rule did stop. The rule now covers every form of force-push and remote deletion.
44. **Two entries in this log said more was fixed than was.** Entry 43 said the permission rules now covered "every form of force-push and remote deletion"; they matched only the flag right after `push`, so `git push origin main --force`, `git push upstream +main` and `git push origin :branch` still fell through to the rule the original force-push was approved under. Entry 42 said the video's sample rate and length "are checked before any upload"; no code did that. Decision D-30 still described the hand-written API-key filter that entry 38 says was replaced. Caught by a code review the owner ran (Claude Opus, high effort), confirmed by reading `.claude/settings.json` and searching `demo/`, `tools/` and CI. Fixed by building what the entries claimed: `tools/guard_commands.py` reads every argument of every command (its `--self-test` checks 33 blocked and 25 allowed forms, in CI too), and `demo/recorder.py --check` reads the finished file back with ffprobe (the published video passes at 24000 Hz and 357.2 s; a generated 22050 Hz file is refused). D-30 rewritten. The brief now says a log entry may only say "fixed" if it names the check that proves it.
45. **The final review found what every earlier review had missed, and two tests pinned the wrong behaviour.** OPERA refusing our credentials dead-lettered postings as rejections, which are never replayed (the twin of the processor fix in entry 40, and `HttpAdaptersTest` asserted it as intended); the scope that lets an app ask for money also let it charge any card token; idempotency keys were one namespace for all clients, so integrators collided and could read each other's results; Cognito's client-credentials tokens, the first authorization server the docs name, were refused for having no audience; a processor success without a reference became a blank reference; a 404 from a wrong address declined cards for good; the webhook relay's window was on creation, so a posting replayed after 30 days was never announced (and a test encoded that window). While scoping keys per client I found a further collision the review had not named: the processor's key was built from the client's key, so two clients' `order-1` would still have met at the processor as a reused key, a decline. Each confirmed by a failing test, fixed, and mutation-checked: 14 of 14 deliberate bugs caught (run by a local script that was not committed).
46. **A guardrail that blocked legitimate work, including its own fix.** The first version of `tools/guard_commands.py` split a command at `|` before reading its quotes, so it refused a read-only `grep 'a\|b'`, and then refused the shell command that would have fixed it. Caught by the hook firing on my own commands as soon as it was live; the file was edited with the editor tool instead, the parser now respects quotes (and checks the raw text when quotes do not balance), and both commands are in the self-test's allowed list.
47. **A reviewer's guess repeated as fact.** The review said Dependabot's `ignore` rules "as far as I know" also suppress security updates, and I wrote that into `.github/dependabot.yml` as a statement. Reading GitHub's options reference before committing showed the opposite: `ignore` is marked as a version-update option, and security updates are not listed as affected (the page states no exception either way, so the comment now says only what the page shows). The narrower ignore list stayed, because it is the better policy whichever way the rule falls.
48. **A style fix that broke the coverage gate.** Adding braces to one-line guard clauses (`if (x) return y;`) put `return y;` on a line of its own, uncovered wherever no test takes that branch; together with new code, `./mvnw verify` failed at 98.89% lines against the 99% gate. Fixed by deleting two getters nothing used and adding the two tests that were missing (a key looked up under another client, scopes sent as a list), not by lowering the gate. That left 99.09% locally, two lines above the gate, and the first push failed CI at 98.9%: on the Linux runner some lines in the race tests run or not depending on thread timing. Fixed by more real coverage (dead accessors removed, an unreachable error path removed by using Spring's own JSON writer, tests for an unparsable health path and for the webhook secret never being printed: 99.5%), and CI now uploads the coverage report, so the next gap can be read instead of guessed.
49. **A convention check that missed a spelling.** The first `CodeConventionsTest` rule against field injection looked for the text `@Autowired`, so `@org.springframework.beans.factory.annotation.Autowired` on a field passed it. Caught by breaking each convention on purpose and running its check (three of four failed as they should; this one did not). The check now matches any qualified spelling of `@Autowired` or `@Inject`, and all four breaks are caught.
50. **Dependency updates left undecided, and a version conflict no test could see.** Seven Dependabot pull requests sat open: each had passed CI alone, nobody had tested the set, and the one marked failed had failed to download Maven, not on its change. When the owner asked why it was not decided, the enforcer's `requireUpperBoundDeps` rule found five libraries running older than the code using them was built for: the AWS SDK's HTTP client on an older httpclient5 than it was compiled against (and an unused Netty client older again), springdoc on older snakeyaml and commons-lang3. `KmsKeyServiceTest` stubs the KMS client, so a mismatch there would first have failed in production, at the first card. Ignoring the majors of build tools had also hidden two critical Vitest advisories, and Dependabot's limit of five open npm pull requests held back a vite security patch. Fixed: the unused Netty client excluded, the four libraries aligned up, `KmsWireTest` runs the real KMS client over HTTP (it fails with `NoClassDefFoundError` on an incompatible httpclient5), the enforcer runs on every build, the seven updates applied and tested together with vite 7 and Vitest 4, and Dependabot now groups minor and patch updates into one pull request per ecosystem.

51. **A simulator that was kinder than the system it stands in for, and a story built on it.** The OPERA simulator spoke a dialect of the bridge's own: its own paths, a flat payment body, and a business date sent with each payment that it refused when it differed from its own. Real OPERA takes no date with a payment (Oracle's `postBillingPayment` has none) and posts on its own business date, so the rejection in agent log 39 and in D-33 could not happen there; the real cost of a stale date is a charge booked on yesterday and posted on today. The first rewrite then invented again: a folio status `Open`, which Oracle's enum does not have. Caught by reading Oracle's published specification, and the second time by `OhipContractTest`, which now checks every exchange against Oracle's Swagger files (D-42; D-33 corrected).
52. **Decimals that lost their trailing zeros.** Read with Jackson's exact decimals, `10.00` became `1E+1`: Jackson strips trailing zeros by default. The simulator refused a payment of 10.00, and the adapter would have failed to read 800.00 back from OPERA, dead-lettering paid postings as unreadable. Caught by the contract test's first run; fixed on both sides (`STRIP_TRAILING_BIGDECIMAL_ZEROES` off), pinned by the 800.00 and three-decimal cases of `OhipContractTest.aPaymentIsPostedAndFoundBackThroughOraclesOperationsInEachCurrency`, which failed when the setting was put back (one of phase 16's six deliberate bugs).
53. **A library chosen by its newest version, not by what it pulls in.** The schema validator's 3.x line is built on Jackson 3 (the offline build failed to resolve it), and its newest 2.x releases ask for a Jackson newer than the one Spring Boot manages, which the enforcer's upper-bound rule refuses. Caught by the build, then by reading each release's POM; 2.0.4 fits. The first candidate, Atlassian's validator, was dropped for the same reason: two Swagger parsers, Guava and a JavaScript engine.
54. **A fail-safe too strict to pay a long stay, a field nobody needed deciding "found", and a demo default in the phase that wrote "fail closed".** Phase 16's adapter looked for its payment before every post, the first one too. It treated a folio window that said `hasMore` as "unavailable", so a guest whose folio ran past one page could never be paid: every attempt and every replay stopped on the same page. The test written for it checked only that a partial window was not read as absent, and nothing asked what happened to the guest. A payment found on the folio was "unavailable" whenever its amount or date could not be read, though only its transaction number decides. Oracle makes the currency optional, so a post whose reply was lost could be dead-lettered on every replay, and a test (`aFoundPaymentWeCannotReadIsAnOutageNotACrash`) pinned that as intended. And the hotel's payment method and cashier defaulted to the simulator's (CC, 9001), so a deployment missing one would post real payments under another cashier. Caught by the owner's code review (`/code-review`, high effort). Each finding was confirmed by a failing test before the fix: `HttpAdapterRepliesTest.aLongFolioIsReadPageByPageSoItsGuestCanBePaid`, `HttpAdapterRepliesTest.aFoundPaymentIsFoundByItsTransactionNumberEvenWhenItsAmountOrDateCannotBeRead`, `FailClosedStartupTest.withoutEachOfTheHotelsOperaSettingsItDoesNotStart`, and `OhipContractTest.aPaymentOnALongFolioIsFoundOnALaterPage` for the simulator's paging. Fixed by reading page by page, with every page that cannot prove absence still "unavailable" (`HttpAdapterRepliesTest.aFolioPageThatCannotProveOurPaymentAbsentIsUnavailableNeverNotFound`). Found payments are now identified by their transaction number, and the settings have no default. Nine bugs put back on purpose, nine caught (each listed in `specs/2026-11-19-p17-ohip-review-fixes/validation.md`). How OPERA really pages is a sandbox question; a wrong guess fails as "unavailable", not as a second post.
55. **Rules that no build checked were broken in the phase that wrote them down, and a reviewer's fix would have contradicted Oracle.**
    - Phase 16 added or touched 73 lines over the 150-character limit that section 3 of the standards sets for new code.
    - It declared the schema validator's version inline, against section 13.
    - Entry 52 of this log said "fixed" without naming the test, against the brief.
    - The OPERA simulator numbered rooms by the count of guests in house, so two guests could share one, and a repeated booking put a guest back to due-in.

    Caught by the owner's code review (`/code-review`, high effort). For its Basic-credentials finding I read Oracle's own description of the header before fixing anything: it asks for plain `ClientID:ClientSecret` under the Basic standard (RFC 7617). So the review's suggested URL encoding was not applied. Its charset point was: Spring defaults to ISO-8859-1, and a euro sign in a secret threw before the request left (`HttpAdapterRepliesTest.theClientIdAndSecretReachOhipAsBasicCredentialsInUtf8ExactlyAsIssued`).

    These checks now run on every build:
    - `CodeConventionsTest.theNumberOfLinesOver150CharactersOnlyGoesDown`: 221 long lines are left, and the count may only fall.
    - `CodeConventionsTest.everyVersionTheBuildDeclaresForADependencyOrAPluginIsAProperty`.
    - `OperaSimulatorTest` for the rooms and repeated bookings.

    Entry 52 now names its test. Eleven deliberate bugs put back, eleven caught (each listed in `specs/2026-11-19-p18-test-names-and-review-cleanup/validation.md`).
56. **A script that rewrote 68 test files split a line at a character inside a string.** To add a `@DisplayName` to every test I used Python's `splitlines()`, which also breaks at U+2028. `SafeTextTest` holds that character inside a string literal, so one of its lines was cut in two. Caught by reading the diff: a change meant only to add lines showed one deletion. The file was restored from the last commit, the script now splits on newlines only, and the rewrite was run again: no deletions, both U+2028 characters intact. The same script missed a test annotated `@org.junit.jupiter.api.Test` (the spelling lesson of entry 49 again). The new display-name check caught it: `CodeConventionsTest.everyTestAndTestClassSaysWhatItProvesInADisplayName`.
57. **The narrated video told two things the code and the contract did not back.** It was introduced as being in the style of Oracle's integration platform, and then said the PMS "pushes a booking event to the bridge", the way the simulator does. Real OPERA Cloud delivers business events on OHIP's Streaming API: a GraphQL subscription over a WebSocket that the consumer opens. Delivery is at least once, and there is no acknowledgement and no dead-letter queue, so the consumer must keep its own offset and skip an event it has already seen. Entry 51 had checked how OPERA takes a payment, not how it announces a booking; Oracle's streaming contract was never among the specifications this repository reads. The script behind the same video still said "nearly four hundred" tests and "thirty six" deliberate bugs when the build had 452 and the README tallied 62: the recorder only refused to record below a floor of 380 tests, and nothing checked the mutation number. Caught when the owner shared another assistant's explanation of the Streaming API. Before any of it went into the video it was checked against Oracle's Streaming Implementation Guide (FAQs; Limitations and Constraints) and the streaming schema in Oracle's hospitality-api-docs repository. Its technical claims held. Its pictures (stock photos, an unrelated diagram, Oracle's logo) were not used. Reading the narration against that contract showed the gap, and reading it against the README showed the counts. The narration now says the simulator posts the event over HTTP and OPERA Cloud would stream it; the architecture page shows the streaming lane marked as not built. The counts are read, not typed: `proof()` in `demo/make_fullflow_demo.py` reads the surefire reports, `jacoco.csv` and the README's mutation tally, puts those numbers on the video's proof card, and refuses to record unless the narration's words hold. The dry run (`DEMO_FAST=1 demo/make_fullflow_demo.py`) asserts the streaming panel, including that the simulator posts over HTTP. Three deliberate breaks of `proof()`'s thresholds (459 tests, 99.5% of lines, 80 mutations) were each refused.
58. **A unit test said a lease was released, and could not fail.** `PostingServiceImplTest` read the lease from the posting object, but the lease is taken by a database update that the unit test mocks, so the object's lease was empty whatever the code did. Caught in the final cleanup: the getters it read were used by nothing in production, and before removing them a mutation stopped the posting from releasing its lease. The unit test still passed; four replay tests failed (`PaymentFlowIntegrationTest.anOperaOutageKeepsTheCapturedPaymentAsAReplayablePostingThatPostsExactlyOnce`, `PaymentFlowIntegrationTest.parallelReplaysOfOneDeadLetteredPostingPostItOnce`, `FullFlowHttpIntegrationTest.anOperaOutageDeadLettersTheCapturedPaymentAndReplayPostsItOnceOperaIsBack`, `FullFlowHttpIntegrationTest.parallelReplaysAgainstANonDeduplicatingOperaPostOnce`). The getters and the empty check are gone, the unit test is named for what it checks (`PostingServiceImplTest.theLeaseRunsFromTheClockForLongerThanOneAttempt`), and `docs/edge-cases.md` names the replay tests as the proof.
59. **The final code review found nine faults in code that earlier phases had passed.** Caught by the owner's request for a final code and security review (`/code-review`, high effort, over the main code, the dashboard, the demo and the tools); each finding was confirmed by reading the code or by a test that failed first, before anything was fixed (entry 47).
