# Decisions

- **D-1 Money is `long` minor units** (cents) plus an ISO currency code. Never floating point.
- **D-2 Idempotency lives in the database.** `charge.idempotency_key` and `posting.idempotency_key` are unique. A parallel twin loses the insert, reads the winner's row and returns it. Same key with different parameters is `409`.
- **D-3 The processor and the PMS are told the same key on every retry** (`key:auth`, `key:cap`, `post:<chargeId>`), so a lost response is retried safely. The safety comes from their idempotency, not from our locking.
- **D-4 A transient failure leaves the charge PENDING; a decline is final.** A PENDING charge is retried with the same key. The outcome names which half happened (`OK`, `DECLINED`, `CHARGE_PENDING`, `CHARGED_NOT_POSTED`).
- **D-5 A post that cannot be made is dead-lettered, never dropped.** Money was taken, so the posting carries a category (`OPERA_UNAVAILABLE`, `REJECTED_BY_OPERA`), an error and an attempt count. An outage can be replayed. A rejection is returned untouched by replay and by a repeated payment: OPERA said no, so it waits for a person to fix the folio. `PostingServiceImplTest.replayingARejectedPostingNeverCallsOperaAgain` checks that the processor-side call count does not move.
- **D-6 The card number is lent, not stored or handed out.** `CardVault.withCard(token, fn)` decrypts, calls `fn`, then zeroes the data key and the decrypted bytes. The vault has no method that returns a PAN, and the only production caller hands it straight to the processor port. This is a convention held by review and by the tests that scan the database and the logs, not by the type system: `Pan` is a public record, so a caller could return it. Zeroing is best effort in a JVM (copies made by the JCA and the AWS SDK are outside our control).
- **D-7 `Pan.toString()` shows the last four only**, and `DataKey.toString()` shows nothing, so an accidental `log.info("{}", pan)` is harmless.
- **D-8 The log mask is defence in depth.** The code never logs a card number; the mask exists for the day someone does. Both are tested.
- **D-9 No CVV is accepted or stored.** A real flow passes it transiently to the processor; this pilot does not model it.
- **D-10 Shadow mode makes the two known drift points explicit** (tax rounding per night or on the total; business date in UTC or the hotel's local day) and runs the same bookings under either rule, so a difference becomes a named decision for the product lead.
- **D-11 Reconciliation exceptions have names** a finance team can act on: `MISSING_IN_SETTLEMENT`, `AMOUNT_DIFFERENCE`, `UNKNOWN_IN_SETTLEMENT`, `NOT_POSTED_TO_PMS`.
- **D-12 Flyway owns the schema on PostgreSQL; Hibernate only validates it** (`ddl-auto=validate` in the `postgres` profile, migrations in `src/main/resources/db/migration`). Tests and the single-app demo still let Hibernate create an in-memory H2 schema. A migration is additive first (add, deploy, then drop in a later release) because two versions run side by side during a rolling deploy. *(Revised 2026-11-18: was `ddl-auto=update`.)*
- **D-13 Synthetic everything,** and the console banner says so.
- **D-14 Layers, not a feature pile.** `api` (controllers, DTOs, one exception handler) calls `service` (interfaces) implemented in `service.impl`, which use `domain` (entities, value objects, pure rules, exceptions), `repository` (Spring Data), `gateway` (ports to the processor and the PMS, with fakes in `gateway.fake`) and `crypto`. Controllers never see a repository or a fake; services never see HTTP; the domain knows no Spring except JPA annotations on its entities (a deliberate shortcut: separate persistence entities would double the model for no gain at this size).
- **D-15 Retry is a Resilience4j policy, injected.** One `Retry` per downstream (processor, PMS), exponential backoff with jitter, only for the exceptions that mean "may not have arrived". The retry wraps each call, so the card number is lent per attempt and is not in memory while a retry waits. Settings: `foliopay.retry.*`.
- **D-16 Concurrency is the database's job.** Unique idempotency keys decide who creates; an `@Version` column decides who may overwrite. A request that loses the version race returns the stored state instead of writing over it.
- **D-17 Fail closed.** Nothing falls back to a demo behaviour. `foliopay.keys` has no default (`local` or `kms`; `local` is refused on any database but in-memory H2 unless explicitly allowed, because its key dies at restart). `foliopay.gateway` has no default: the fake processor and fake PMS are beans only when it is `fake`, so a start without it fails instead of answering OK to payments that moved no money. The vault view, log tail, fault switches, shadow runs and the OpenAPI description exist only in the demo profile. The app binds to loopback and refuses any `Host` header off an allowlist.
- **D-18 "Today" is the hotel's day.** The default business date comes from a `Clock` in `foliopay.business-zone` (Asia/Dubai), not the JVM zone, which is UTC in a container. In a real deployment the PMS's own business date (night audit) is authoritative.
- **D-19 A payment link has one claim at a time.** Paying atomically moves the link OPEN to PAYING for one card (a conditional update, so two cards cannot both win). A repeat by the same card resumes the same idempotent charge, key `link:<id>:<sha256(token)[:16]>` (the token itself is never in a key). Another card is refused while PAYING (409) and after PAID (410). A capture makes it PAID, a decline gives it back (OPEN), a pending charge keeps the claim. A unique `open_slot` allows one live link per booking, and a booking change while PAYING waits.
- **D-20 Errors are one safe shape.** Domain exceptions map to 400/404/409/410 in one `@RestControllerAdvice`; validation errors name the field, never the value; anything unexpected is a generic 500. *(Revised 2026-11-18, D-29: the full exception is now logged with the request id; the body still says nothing.)*
- **D-21 An idempotency key binds the whole request.** The charge stores booking, folio and business date as well as card and amount; a repeat that differs in any of them is 409, never a silent OK for the original. A repeat that names **no** business date means "the date this charge was taken on", so a charge left pending before night audit can still be resumed after it; only a new charge asks the PMS for the date. *(Clarified 2026-11-18, owner approved.)*
- **D-22 When two requests race, the one that knows more wins.** CAPTURED beats DECLINED beats PENDING, and POSTED beats DEAD_LETTER beats PENDING. On a lost optimistic lock the stored state is reloaded and our result is carried onto it only if ours is further along.
- **D-23 OPERA is a port with two possible adapters** (OPERA Cloud/OHIP and OPERA 5). A card payment is a payment to a reservation's folio window with a payment code and a cashier, not a charge. OPERA is not assumed to deduplicate: before any later attempt the service looks for its own reference. The hotel's business date comes from the PMS (it moves at night audit), and a client-supplied date must equal it. Only the fake adapter exists; the hotel id, window, payment code and cashier are configuration.
- **D-24 Text from outside is data.** Booking and folio ids are restricted to `[A-Za-z0-9._-]{1,64}`; processor and PMS messages are flattened to one line and cut to 255 characters before they are stored or logged; the log converter masks card numbers (including numbers glued to other digits, odd separators and Unicode digits) in messages and in exception text and escapes line breaks; CSV references must be plain. Nothing read from the database, logs, CSV or PMS is an instruction for a person or an agent (see SECURITY.md).
- **D-25 A capture decline after authorisation releases the hold.** The processor port has `voidAuthorization`. A crash between authorisation and capture is not covered (no sweeper yet).
- **D-26 The outside world is simulated over HTTP, not faked in memory.** The OPERA and processor simulators are separate services (same jar, different main class and base package, so the bridge never scans them). The bridge's HTTP adapters carry the real concerns: timeouts, status mapping, OAuth refresh, the idempotency header, look-before-repost. They are not Oracle software and their resource paths are simplified; a real OHIP adapter must verify them. There is no public Docker image of OPERA: the realistic next step is the OHIP sandbox.
- **D-27 A timeout is "unknown", never "failed".** A read timeout or connection error from OPERA or the processor means the call may have landed; the bridge retries with the same key (processor) or looks for its own reference first (OPERA) instead of assuming the money did not move.
- **D-28 One request at a time talks to OPERA about a posting (a lease).** OPERA does not deduplicate, so two requests that both look, find nothing and post would credit the folio twice. Before an attempt a request takes a lease in the database (`lease_until`, `lease_owner`, a conditional update); before each post it renews the lease and does not post if it lost it. The lease length is derived from the timeouts and the retry policy (`ResilienceConfig.postingLease`: every try is a look and a post, each up to four HTTP exchanges, doubled, never under a minute), so a slower configuration cannot outrun it. A lease that ran out (a crashed request) can be taken over. Lease times come from each instance's clock, so instances must keep time in sync (Amazon Time Sync on AWS); the doubling covers seconds of drift. *(Owner approved 2026-11-18.)*
- **D-29 Every error body carries a stable code; retryable ones carry `Retry-After`.** `{"error": "...", "code": "..."}`. The two 409s mean opposite things: `IDEMPOTENCY_KEY_REUSED` is final (the client sent a different request under an old key), `CONCURRENT_UPDATE` and `PAYMENT_IN_PROGRESS` mean send the same request again later. `DOWNSTREAM_UNAVAILABLE` (503) is retryable with the same key. Statuses are unchanged, so existing clients keep working. Every request gets an `X-Request-Id` (kept from the caller if it is plain, otherwise generated) that is in every log line. An unexpected error is logged with the class and stack trace of every exception in its cause chain but **no message** (`Redacted`): a message can carry request data the Luhn mask cannot recognise (a mistyped or split card number), so it is dropped rather than masked, which keeps hard rule 1. *(The IETF idempotency-key draft answers a reused key with 422; changing the status is a breaking change and is left to the owner.)*
- **D-30 Every `/api` call is authenticated with an API key (until OAuth2 replaces it).** `Authorization: Bearer <key>`; only the SHA-256 of each key is configured (`foliopay.auth.api-keys=name:sha256hex,...`, from Secrets Manager), compared in constant time; the client name is in every log line of the request. Fails closed: with a real gateway and no keys the application does not start, unless `foliopay.auth.disabled=true` is set by name (the Compose demo only). Health probes are open; they say only UP or DOWN. Chosen over Spring Security for now because it needs no new dependency and is enough to stop anonymous card testing; per-endpoint roles, overlapping key rotation and OAuth2 client credentials are the next step.
- **D-31 A card token stores the KMS key ARN that wrapped it.** New data keys come from the configured key (an alias is fine); `GenerateDataKey` reports the key's ARN, which is stored in `card_token.key_id` and named on every `Decrypt`. Moving the alias to a new key (manual rotation, or after a compromise) therefore leaves older cards readable, and the application never needs to know the alias history.
- **D-32 Reconciliation is scoped to the statement's period.** The expected side is the captures taken on the statement's business dates plus any capture the statement names (a late settlement of an older capture is matched, not "unknown"). Only those rows and their postings are read, never whole tables, and `IN (...)` lists are sent in slices of 1,000 (PostgreSQL's driver refuses more than 65,535 parameters in one statement). A reference settled in more than one currency gives one item per currency; amounts are never summed across currencies (D-1). Without a period, every capture ever made is expected (demos and small pilots only).
- **D-33 The business date is the PMS's latest answer, and never older than it has to be.** An answer is stale only if the answer to a later request already arrived, so a slow reply from before night audit cannot undo the audit; otherwise the PMS's latest answer wins, also a date the hotel corrected backwards (a rule of "the latest date wins" would ignore that correction until a restart: caught by an older integration test, agent log 41). The PMS is asked for every new charge, including right after an outage, and its first answer is used at once. *Considered and rejected:* not asking a failing PMS again for 30 s, so that during an outage one payment waits for the timeout instead of each one. The full-flow demo's dry run showed the cost: OPERA came back after a night audit that ran during the outage, the bridge kept yesterday's date for the quiet period, and OPERA rejected the posting for good (agent log 39). A payment during an outage waits 2 to 5 s for the timeout instead; correctness of the folio wins over that latency. Business dates are never cached while the PMS is healthy, for the same reason.
- **D-34 The processor refusing the request is final, like a decline, but it is our problem.** A 4xx other than 402, 429, 401/403 and an in-progress 409 (unknown authorisation, amount mismatch, an idempotency key reused with a different request) becomes `PspRejectedException`: the charge is DECLINED with the processor's code, a hold is released, and it is logged as an error for an operator. A 401 or 403 means our credentials were refused (a rotated key, a proxy): that says nothing about the guest's card, so it is transient and the charge stays PENDING until the key is fixed, instead of declining that card on that link for good. Anything we cannot classify (an unreadable reply, a bug) leaves the charge PENDING and saved, and the hold in place, because the capture may have happened: a retry with the same key asks the processor again (D-27).
- **D-35 The integrator learns what happened by signed webhook, from the database, at least once.** See the phase 14 spec. Each event (`payment.captured`, `payment.declined`, `folio.posted`, `folio.dead_lettered`) is derived from the state already stored, so there is no second write to forget and no event for a state that was rolled back. Deliveries are signed (HMAC-SHA256 over the timestamp and the body), carry a stable event id for the receiver to deduplicate, are retried with backoff and end DELIVERED or FAILED, never dropped. No card data and no card token is ever in a payload. The relay looks back `foliopay.webhook.lookback` (30 days) so each run reads recent rows only; a relay stopped for longer than that would not announce older payments, so it is alarmed on long before.
- **D-36 AI guardrails are enforced, not only written down.** The hard rules in `CLAUDE.md` are backed by `tools/guard_secrets.py`: a Claude Code `PreToolUse` hook (`.claude/settings.json`) blocks any file write, edit or shell command that carries a Luhn-valid card number outside the public test list, a CVV value, or a credential pattern; CI runs the same scan over every tracked file. The project settings also deny reading secrets and force-pushing, and ask before any commit, push or AWS command. Runtime text is data, never instructions (D-24, SECURITY.md).
- **D-37 Payment requests from apps live apart from bookings.** A request created through `POST /api/links` is stored under `req:<reference>`; a booking reference can never contain a colon, so an app's request never replaces a booking's deposit link (nor the reverse), and a client with `payments:write` cannot change what only `bookings:write` may.
- **D-38 The operator dashboard is a single-page app on the same API, behind the same rules.** React 18 and TypeScript, built with Vite, served by Spring Boot at `/dashboard/` and built and tested by Maven (`frontend-maven-plugin` with a pinned Node), so the jar and the Docker image always carry the version that was tested. It reads only the public API with the same scopes as any client (`payments:read` to look, `operations` to replay, redeliver and reconcile); the figures on its front page come from one `GET /api/overview` computed by the database, never by paging through lists in the browser. Sign-in is OpenID Connect, authorization code with PKCE, at the company's identity provider; the access token is held in memory only; the content security policy allows scripts from this origin only and connections to this origin and the identity provider only. With the API open (demo, fake gateway) it needs no sign-in; with the API protected and no identity provider configured it says so instead of half-working. Hash routing, so the server needs no fallback route. No UI kit and no state library: five screens do not need them. The classic console stays at `/` for the recorded demo.
