# Decisions

- **D-1 Money is `long` minor units** (cents) plus an ISO currency code. Never floating point.
- **D-2 Idempotency lives in the database.** `(charge.client_id, charge.idempotency_key)` and `posting.idempotency_key` are unique (keys are per client, D-40). A parallel twin loses the insert, reads the winner's row and returns it. Same key with different parameters is `409`.
- **D-3 The processor and the PMS are told the same key on every retry** (`<chargeId>:auth`, `<chargeId>:cap`, `<chargeId>:void`, `post:<chargeId>`), so a lost response is retried safely. The safety comes from their idempotency, not from our locking. The processor's key is the charge's own id, not the client's key: unique across clients, and the same for a parallel twin, which reads the winner's row. *(Changed 2026-11-18 in the production-readiness review the owner asked for.)* It was `<client key>:auth`, which two clients using the same key would have shared at the processor (a reused-key refusal, so a decline). A deployment with charges still PENDING under the old keys must resume those with the old form.
- **D-4 A transient failure leaves the charge PENDING; a decline is final.** A PENDING charge is retried with the same key. The outcome names which half happened (`OK`, `DECLINED`, `CHARGE_PENDING`, `CHARGED_NOT_POSTED`).
- **D-5 A post that cannot be made is dead-lettered, never dropped.** Money was taken, so the posting carries a category (`OPERA_UNAVAILABLE`, `REJECTED_BY_OPERA`), an error and an attempt count. An outage can be replayed. A rejection is returned untouched by replay and by a repeated payment: OPERA said no, so it waits for a person to fix the folio. `PostingServiceImplTest.replayingARejectedPostingNeverCallsOperaAgain` checks that the processor-side call count does not move.
- **D-6 The card number is lent, not stored or handed out.** `CardVault.withCard(token, fn)` decrypts, calls `fn`, then zeroes the data key and the decrypted bytes. The vault has no method that returns a PAN, and the only production caller hands it straight to the processor port. This is a convention held by review and by the tests that scan the database and the logs, not by the type system: `Pan` is a public record, so a caller could return it. Zeroing is best effort in a JVM (copies made by the JCA and the AWS SDK are outside our control).
- **D-7 `Pan.toString()` shows the last four only**, and `DataKey.toString()` shows nothing, so an accidental `log.info("{}", pan)` is harmless.
- **D-8 The log mask is defence in depth.** The code never logs a card number; the mask exists for the day someone does. Both are tested.
- **D-9 No CVV is accepted or stored.** A real flow passes it transiently to the processor; this pilot does not model it.
- **D-10 Shadow mode makes the two known drift points explicit** (tax rounding per night or on the total; business date in UTC or the hotel's local day) and runs the same bookings under either rule, so a difference becomes a named decision for the product lead.
- **D-11 Reconciliation exceptions have names** a finance team can act on: `MISSING_IN_SETTLEMENT`, `AMOUNT_DIFFERENCE`, `UNKNOWN_IN_SETTLEMENT`, `NOT_POSTED_TO_PMS`.
- **D-12 Flyway owns the schema on PostgreSQL; Hibernate only validates it** (`ddl-auto=validate` in the `postgres` profile, migrations in `src/main/resources/db/migration`). Tests and the single-app demo still let Hibernate create an in-memory H2 schema. A migration is additive first (add, deploy, then drop in a later release) because two versions run side by side during a rolling deploy. Referential integrity is in the database too (V2: a charge names a stored card, a posting names a charge), although the entities refer to each other by id, not by JPA association, so no lazy loading or N+1 query can hide in a payment path. The migrations run on PostgreSQL 16 in the Compose stack, not in the unit test run, which uses H2: Testcontainers would close that gap (a test dependency, for the owner to approve). *(Revised 2026-11-18: was `ddl-auto=update`.)*
- **D-13 Synthetic everything,** and the console banner says so.
- **D-14 Layers, not a feature pile.** `api` (controllers, DTOs, one exception handler) calls `service` (interfaces) implemented in `service.impl`, which use `domain` (entities, value objects, pure rules, exceptions), `repository` (Spring Data), `gateway` (ports to the processor and the PMS, with fakes in `gateway.fake`) and `crypto`. Controllers never see a repository or a fake; services never see HTTP; the domain knows no Spring except JPA annotations on its entities (a deliberate shortcut: separate persistence entities would double the model for no gain at this size).
- **D-15 Retry is a Resilience4j policy, injected.** One `Retry` per downstream (processor, PMS), exponential backoff with jitter, only for the exceptions that mean "may not have arrived". The retry wraps each call, so the card number is lent per attempt and is not in memory while a retry waits. Settings: `foliopay.retry.*`.
- **D-16 Concurrency is the database's job.** Unique idempotency keys decide who creates; an `@Version` column decides who may overwrite. A request that loses the version race returns the stored state instead of writing over it.
- **D-17 Fail closed.** Nothing falls back to a demo behaviour. `foliopay.keys` has no default (`local` or `kms`; `local` is refused on any database but in-memory H2 unless explicitly allowed, because its key dies at restart). `foliopay.gateway` has no default: the fake processor and fake PMS are beans only when it is `fake`, so a start without it fails instead of answering OK to payments that moved no money. The vault view, log tail, fault switches, shadow runs and the OpenAPI description exist only in the demo profile. The app binds to loopback and refuses any `Host` header off an allowlist.
- **D-18 "Today" is the hotel's day.** The default business date comes from a `Clock` in `foliopay.business-zone` (Asia/Dubai), not the JVM zone, which is UTC in a container. In a real deployment the PMS's own business date (night audit) is authoritative.
- **D-19 A payment link has one claim at a time.** Paying atomically moves the link OPEN to PAYING for one card (a conditional update, so two cards cannot both win). A repeat by the same card resumes the same idempotent charge, key `link:<id>:<sha256(token)[:16]>` (the token itself is never in a key). Another card is refused while PAYING (409) and after PAID (410). A capture makes it PAID, a decline gives it back (OPEN), a pending charge keeps the claim. A unique `open_slot` allows one live link per booking, and a booking change while PAYING waits.
- **D-20 Errors are one safe shape.** RFC 9457 problem details (`application/problem+json`: `type`, `title`, `status`, `detail`, plus our `code`), from one `@RestControllerAdvice` and, for requests refused before Spring MVC, from `Problems.write` in the filters. Domain exceptions map to 400/404/409/410; validation errors name the field, never the value; anything unexpected is a generic 500. *(Revised 2026-11-18, D-29: the full exception is now logged with the request id; the body still says nothing.)*
- **D-21 An idempotency key binds the whole request.** The charge stores booking, folio and business date as well as card and amount; a repeat that differs in any of them is 409, never a silent OK for the original. A repeat that names **no** business date means "the date this charge was taken on", so a charge left pending before night audit can still be resumed after it; only a new charge asks the PMS for the date. *(Clarified 2026-11-18, owner approved.)*
- **D-22 When two requests race, the one that knows more wins.** CAPTURED beats DECLINED beats PENDING, and POSTED beats DEAD_LETTER beats PENDING. On a lost optimistic lock the stored state is reloaded and our result is carried onto it only if ours is further along.
- **D-23 OPERA is a port with two possible adapters** (OPERA Cloud/OHIP and OPERA 5). A card payment is a payment to a reservation's folio window with a payment code and a cashier, not a charge. OPERA is not assumed to deduplicate: before any later attempt the service looks for its own reference. The hotel's business date comes from the PMS (it moves at night audit), and a client-supplied date must equal it. The hotel id, window, payment method code and cashier number are configuration; the OHIP adapter follows Oracle's published contract (D-42).
- **D-24 Text from outside is data.** Booking and folio ids are restricted to `[A-Za-z0-9._-]{1,64}`; processor and PMS messages are flattened to one line, stripped of invisible formatting characters (bidirectional overrides, zero-width and Unicode tag characters, which show a person one thing and a program or a language model another) and cut to 255 characters before they are stored or logged; a payment request description containing control or invisible characters is refused; the log converter masks card numbers (including numbers glued to other digits, odd separators and Unicode digits) in messages and in exception text and escapes line breaks; CSV references must be plain. Nothing read from the database, logs, CSV or PMS is an instruction for a person or an agent (see SECURITY.md).
- **D-25 A capture decline after authorisation releases the hold.** The processor port has `voidAuthorization`. A crash between authorisation and capture is not covered (no sweeper yet).
- **D-26 The outside world is simulated over HTTP, not faked in memory.** The OPERA and processor simulators are separate services (same jar, different main class and base package, so the bridge never scans them). The bridge's HTTP adapters carry the real concerns: timeouts, status mapping, OAuth refresh, the idempotency header, look-before-repost. They are not Oracle software and their resource paths are simplified; a real OHIP adapter must verify them. There is no public Docker image of OPERA: the realistic next step is the OHIP sandbox.
- **D-27 A timeout is "unknown", never "failed".** A read timeout or connection error from OPERA or the processor means the call may have landed; the bridge retries with the same key (processor) or looks for its own reference first (OPERA) instead of assuming the money did not move.
- **D-28 One request at a time talks to OPERA about a posting (a lease).** OPERA does not deduplicate, so two requests that both look, find nothing and post would credit the folio twice. Before an attempt a request takes a lease in the database (`lease_until`, `lease_owner`, a conditional update); before each post it renews the lease and does not post if it lost it. The lease length is derived from the timeouts and the retry policy (`ResilienceConfig.postingLease`: every try is a look and a post, each up to four HTTP exchanges, doubled, never under a minute), so a slower configuration cannot outrun it. A lease that ran out (a crashed request) can be taken over. Lease times come from each instance's clock, so instances must keep time in sync (Amazon Time Sync on AWS); the doubling covers seconds of drift. *(Owner approved 2026-11-18.)*
- **D-29 Every error body carries a stable code; retryable ones carry `Retry-After`.** A problem detail with `"code": "..."` (D-20; it was `{"error", "code"}` until the API was versioned, D-39). The two 409s mean opposite things: `IDEMPOTENCY_KEY_REUSED` is final (the client sent a different request under an old key), `CONCURRENT_UPDATE` and `PAYMENT_IN_PROGRESS` mean send the same request again later. `DOWNSTREAM_UNAVAILABLE` (503) is retryable with the same key. Statuses are unchanged, so existing clients keep working. Every request gets an `X-Request-Id` (kept from the caller if it is plain, otherwise generated) that is in every log line. An unexpected error is logged with the class and stack trace of every exception in its cause chain but **no message** (`Redacted`): a message can carry request data the Luhn mask cannot recognise (a mistyped or split card number), so it is dropped rather than masked, which keeps hard rule 1. *(The IETF idempotency-key draft answers a reused key with 422; changing the status is a breaking change and is left to the owner.)*
- **D-30 Every `/api` call is authenticated, by Spring Security, and limited by scope.** OAuth2 client credentials (preferred): the bridge is a resource server and checks a JWT's signature against the authorization server's JWKS, the issuer, the expiry, that it is an access token (`token_use`, when present, must be `access`), and that it is meant for this API: the `aud` claim where the server sets one, or the scope prefix where it does not (Amazon Cognito's client-credentials tokens have no `aud`; with a prefix configured only scopes carrying it count). API keys for integrators that cannot do OAuth2: `X-Api-Key`, configured as `name:sha256hex:scopes` (only the hash, from Secrets Manager), compared in constant time; an unknown key is refused, never treated as anonymous. The client (the token's `client_id`, else its subject, or the key's name) is in every log line and owns its idempotency keys (D-40). Scopes: `cards:write`, `payments:write`, `links:write`, `bookings:write`, `payments:read`, `operations` (anything not listed, least access). Fails closed: with a real gateway and no authentication, or OAuth2 without an issuer or without an audience or scope prefix, the application does not start; `foliopay.auth.disabled=true` exists by name for the Compose demo only. Health probes are open; they say only UP or DOWN. *(Rewritten 2026-11-18: this record still described the first, hand-written `Authorization: Bearer <key>` filter after the owner had it replaced by Spring Security, agent log 38 and 44.)*
- **D-31 A card token stores the KMS key ARN that wrapped it.** New data keys come from the configured key (an alias is fine); `GenerateDataKey` reports the key's ARN, which is stored in `card_token.key_id` and named on every `Decrypt`. Moving the alias to a new key (manual rotation, or after a compromise) therefore leaves older cards readable, and the application never needs to know the alias history.
- **D-32 Reconciliation is scoped to the statement's period.** The expected side is the captures taken on the statement's business dates plus any capture the statement names (a late settlement of an older capture is matched, not "unknown"). Only those rows and their postings are read, never whole tables, and `IN (...)` lists are sent in slices of 1,000 (PostgreSQL's driver refuses more than 65,535 parameters in one statement). A reference settled in more than one currency gives one item per currency; amounts are never summed across currencies (D-1). Without a period, every capture ever made is expected (demos and small pilots only).
- **D-33 The business date is the PMS's latest answer, and never older than it has to be.** An answer is stale only if the answer to a later request already arrived, so a slow reply from before night audit cannot undo the audit; otherwise the PMS's latest answer wins, also a date the hotel corrected backwards (a rule of "the latest date wins" would ignore that correction until a restart: caught by an older integration test, agent log 41). The PMS is asked for every new charge, including right after an outage, and its first answer is used at once. *Considered and rejected:* not asking a failing PMS again for 30 s, so that during an outage one payment waits for the timeout instead of each one. The full-flow demo's dry run showed the cost: OPERA came back after a night audit that ran during the outage, the bridge kept yesterday's date for the quiet period, and OPERA rejected the posting for good (agent log 39). *(Corrected 2026-11-18, D-42: the rejection came from the simulator, which refused a posting whose date differed from its own; real OPERA takes no date with a payment and posts on its own business date. The cost of a stale date is real but different: the bridge records the charge on yesterday while OPERA posts it on today, a difference reconciliation must explain. The decision stands.)* A payment during an outage waits 2 to 5 s for the timeout instead; correctness of the folio wins over that latency. Business dates are never cached while the PMS is healthy, for the same reason.
- **D-34 The processor refusing the request is final, like a decline, but it is our problem.** A 4xx other than 402, 408, 429, 401/403, a 404 without the processor's own error code, and an in-progress 409 (unknown authorisation, amount mismatch, an idempotency key reused with a different request) becomes `PspRejectedException`: the charge is DECLINED with the processor's code, a hold is released, and it is logged as an error for an operator. A 401 or 403 means our credentials were refused (a rotated key, a proxy): that says nothing about the guest's card, so it is transient and the charge stays PENDING until the key is fixed, instead of declining that card on that link for good. Anything we cannot classify (an unreadable reply, a success without a reference, a bug) leaves the charge PENDING and saved, and the hold in place, because the capture may have happened: a retry with the same key asks the processor again (D-27). The same rule holds for OPERA: our credentials refused (the token endpoint's 4xx, a 401 after a fresh token, a 403) or a 404 that is not OPERA's own answer dead-letters the posting as `OPERA_UNAVAILABLE`, which can be replayed once the configuration is fixed, never as `REJECTED_BY_OPERA`, which waits for a person to repair a folio that is fine. *(Changed 2026-11-18 in the production-readiness review the owner asked for.)*
- **D-35 The integrator learns what happened by signed webhook, from the database, at least once.** See the phase 14 spec. Each event (`payment.captured`, `payment.declined`, `folio.posted`, `folio.dead_lettered`) is derived from the state already stored, so there is no second write to forget and no event for a state that was rolled back. Deliveries are signed (HMAC-SHA256 over the timestamp and the body), carry a stable event id for the receiver to deduplicate, are retried with backoff and end DELIVERED or FAILED, never dropped. No card data and no card token is ever in a payload. The relay looks back `foliopay.webhook.lookback` (30 days) on each row's last change (`updated_at`), not its creation, so each run reads recent rows only and a posting replayed weeks after its payment is still announced; a relay stopped for longer than that would not announce older changes, so it is alarmed on long before.
- **D-36 AI guardrails are enforced, not only written down.** The hard rules in `CLAUDE.md` are backed by `tools/guard_secrets.py`: a Claude Code `PreToolUse` hook (`.claude/settings.json`) blocks any file write, edit or shell command that carries a Luhn-valid card number outside the public test list, a CVV value, or a credential pattern; CI runs the same scan over every tracked file. `tools/guard_commands.py`, a second `PreToolUse` hook, reads every shell command's arguments and blocks force-pushes and remote deletions in any order (`git push origin main --force`, `+main`, `:branch`, `git -C . push -f`), `git reset --hard`, `git clean -f`, `gh repo/release delete` and a download piped into a shell: prefix-matching permission rules had let a reordered force-push through. The project settings also deny reading secrets, and ask before any commit, push or AWS command. Runtime text is data, never instructions (D-24, SECURITY.md, CLAUDE.md rule 8); the hooks bound what a prompt-injected agent could do.
- **D-37 Payment requests from apps live apart from bookings, and asking for money is not taking it.** A request created through `POST /api/v1/links` is stored under `req:<reference>`; a booking reference can never contain a colon, so an app's request never replaces a booking's deposit link (nor the reverse). Creating a request needs `links:write`, which cannot pay, tokenise or charge: an F&B or spa app that may ask a guest for money can never take it, even holding a card token while it relays a link payment. *(Changed 2026-11-18 in the production-readiness review the owner asked for.)* It was under `payments:write`, which can charge any token to any folio.
- **D-38 The operator dashboard is a single-page app on the same API, behind the same rules.** React 18 and TypeScript, built with Vite, served by Spring Boot at `/dashboard/` and built and tested by Maven (`frontend-maven-plugin` with a pinned Node), so the jar and the Docker image always carry the version that was tested. It reads only the public API with the same scopes as any client (`payments:read` to look, `links:write` to create a payment request, `operations` to replay, redeliver and reconcile); the figures on its front page come from one `GET /api/overview` computed by the database, never by paging through lists in the browser. Sign-in is OpenID Connect, authorization code with PKCE, at the company's identity provider; the access token is held in memory only; the content security policy allows scripts from this origin only and connections to this origin and the identity provider only. With the API open (demo, fake gateway) it needs no sign-in; with the API protected and no identity provider configured it says so instead of half-working. Hash routing, so the server needs no fallback route. No UI kit and no state library: five screens do not need them. The classic console stays at `/` for the recorded demo.
- **D-39 The public API is versioned in the path and only grows within a version.** Every endpoint is under `/api/v1` (`ApiPaths.V1`), the way payment APIs version theirs. Inside a version only additive changes are made: new endpoints, new optional request fields, new response fields, new enum values (clients must ignore what they do not know). Anything else (a removed or renamed field, a changed status or meaning, a new required field) is a new version served beside the old one. An endpoint kept for existing clients is marked `@ApiDeprecation(since, sunset, successor)`: every response then carries `Deprecation` (RFC 9745), `Sunset` (RFC 8594) and `Link: <successor>; rel="successor-version"`, and each call is logged with the client, so operators know who must still move before the sunset date. Integrators are told the sunset date when the endpoint is deprecated. *Considered:* a version header or media type (`Accept: application/vnd...v2+json`), which keeps URLs stable but hides the version from logs, caches and the person reading a URL; Spring Framework 7 adds built-in versioning, to adopt with Spring Boot 4. *(Added 2026-11-18; before this the API was unversioned at `/api`, with no clients yet, so no alias was kept.)*
- **D-40 An idempotency key belongs to the client that sent it.** `charge.client_id` is the authenticated client (D-30) and the key is unique per client, so two integrators that both use `order-1001` get two payments, and neither can read the other's result by replaying its key; the processor gets the charge's own id (D-3). The bridge's own keys (payment links, shadow runs) share one namespace, `''`, so a link paid through any client is one charge. A client that changes its identity (a new OAuth client in place of an API key) must finish its pending charges first, or resume them under the old identity. *(Added 2026-11-18, found by the final review; Stripe and Adyen scope keys per account the same way.)*
- **D-41 Logs say what happened to each payment, and nothing that could be used against it.** INFO and above for every change of a charge's, posting's, link's or webhook's state, with ids, keys, amounts and statuses; DEBUG (`LOGGING_LEVEL_DEV_FOLIOPAY=DEBUG`) for the decisions in between. Never a card number (hard rule 1, D-8) and never a card token, which can be charged by whoever holds it: `PciIntegrationTest` runs a full flow at DEBUG and checks the raw events for both. No aspect that logs every method's parameters: it would log whatever a future parameter holds. Production logs one masked JSON object per line (`logback-json.xml`, chosen with `LOGGING_CONFIG`), with the request id and client as fields for CloudWatch Logs Insights; the text format stays for local runs. *(Added 2026-11-18.)*
- **D-42 The OPERA adapter and the simulator follow Oracle's published OHIP contract, and a test holds both to it.** OPERA cannot be installed or run locally: OPERA Cloud is Oracle's hosted service, OPERA 5 is licensed to hotels, and real access comes from Oracle's partner sandbox or a hotel's test environment through the employer. So the closest thing to the real system is Oracle's own specification (github.com/oracle/hospitality-api-docs, UPL licence). The adapter uses its operations: `getToken` (client id and secret as HTTP Basic, `x-app-key`, `enterpriseId`, a scope), `getBusinessDate` (`/bof/v1`, a list of hotels), `postBillingPayment` (`/csh/v1`, a `criteria` object: the reservation, the folio window, the cashier as a number, the hotel's payment method code, the amount as a decimal number, our key as the posting reference, the processor's reference as the remark, action `Billing`) and `getFolio` (read back to find our posting, a `Payment` with our reference; a window that says it has more cannot prove absence, so that is "unavailable", never "not there"). Errors are Oracle's problem details, the code in `o:errorCode`. OPERA posts on its own business date: a payment carries no date, so nothing can be "rejected for the wrong business date". `OhipContractTest` records every exchange between the adapter and the simulator, in the happy path and each failure, and checks it against Oracle's Swagger files, trimmed to these operations by `tools/ohip_specs.py` at a pinned commit (`src/test/resources/ohip`); objects are read strictly (only the fields Oracle defines) and a date may be ISO length (Oracle's `maxLength: 8` contradicts its own `format: date`). *Still to confirm in a sandbox, listed in `specs/roadmap.md`:* whether OHIP's 201 carries the postings or only a `Location` (the adapter handles both: without a transaction number it looks before posting again); the sign of a payment on a folio (handled either way); payments before arrival as deposits (`action: Deposit`); the status of a reservation lock (the simulator's 409 is an assumption). *(Added 2026-11-18. Before this the adapter and the simulator spoke an OHIP-style dialect of the bridge's own: `/v1/hotels/{h}/business-date`, a flat body with a business date that the simulator refused when it differed, a lookup by reference that OHIP does not have, and errors under `code`.)*
